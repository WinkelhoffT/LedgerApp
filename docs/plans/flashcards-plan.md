# Feature Plan: AI Flashcard Generation (Anki CSV Export)

Status: Draft — waiting for confirmation
Classification (per `CLAUDE.md`): **Large** (AI integration) — implementation starts only after
this plan is reviewed and explicitly confirmed.

## 1. Goal

Let a student turn an existing **Markdown note** or an uploaded **document** (PDF/DOCX) into a
deck of flashcards generated by Claude via the Anthropic API, review and edit the cards in
StudyHub, and export the deck as a **CSV file that Anki can import directly**.

In line with `CLAUDE.md` ("AI Features"), the cards should help the student *learn* the material:
each card asks about one concept and the answer explains it. Cards are never "solutions" to
assignments or exams.

## 2. Scope

In scope:

- Generate a deck from exactly one source: a `Note` or a `Document` (PDF, DOCX).
- Options per generation: target number of cards (e.g. 5–50), card language (source language /
  German / English), optional focus hint (free text, e.g. "only chapter 3", "definitions").
- Persist the generated deck and its cards (owned by the source's `Course` or `Semester`).
- List decks, view a deck, edit / delete single cards, archive a deck (soft delete).
- Export a deck as Anki-compatible CSV (`Front;Back;Tags`) and download it from the UI.
- Replace the "coming soon" placeholder on `/flashcards` with the real page.

Out of scope (later milestones):

- Studying / spaced repetition inside StudyHub (Anki does that).
- Direct `.apkg` export or AnkiConnect sync.
- Cloze cards, image cards (Basic front/back only for now).
- Generating from several sources at once, or from a whole course.
- Streaming the generation progress card-by-card into the UI.
- Usage/cost tracking dashboard.

## 3. Decisions

### 3.1 Claude API access

- **Official Anthropic C# SDK** (NuGet `Anthropic`), no hand-written HTTP client.
- **Model: `claude-opus-5-5`**, configurable via options (`Anthropic:Model`) so it can be switched
  (e.g. to `claude-sonnet-5-5` for lower cost) without code changes.
- **Effort: `medium`** (set explicitly via `OutputConfig.Effort`; extracting and phrasing cards is
  not a hard reasoning task). Configurable (`Anthropic:Effort`).
- **Structured output** (`OutputConfig.Format` with a JSON schema) so the response is guaranteed to
  be `{ "cards": [ { "front": string, "back": string, "tags": string[] } ] }` — no fragile
  parsing of free text, no assistant prefill (not supported on current models).
- **Input:**
  - Note → Markdown text as a text content block.
  - PDF → `DocumentBlockParam` with `Base64PdfSource` (Claude reads text *and* layout/figures).
    API limits: 32 MB per request, 600 pages. The existing 25 MB upload cap stays below that.
  - DOCX → Claude has no native DOCX input, so the text is extracted first
    (`DocumentFormat.OpenXml`) and sent as plain text.
- **Refusals / errors:** check `StopReason` (`refusal`, `max_tokens`) before reading content; map
  SDK exceptions (rate limit, 5xx, auth) to a `FlashcardGenerationFailedException` with an error
  code. Enable the server-side refusal fallback (`fallbacks: "default"`) as recommended for this
  model.
- **API key:** `ANTHROPIC_API_KEY` environment variable / user-secrets only — never in a committed
  `appsettings.json`. `docker-compose.yml` passes it through to `studyhub-api` only; the UI
  container never sees it. If no key is configured, the feature reports a clear
  "AI not configured" error instead of crashing at startup.
- **Prompt (system):** fixed, versioned in code; instructs Claude to
  - create atomic cards (one fact/concept per card), questions that require understanding,
    answers that briefly explain *why*;
  - stick strictly to the provided material (no invented facts), preserve technical correctness,
    keep code/formulas intact;
  - not produce solutions to assignments/exams contained in the material;
  - use HTML for formatting in answers (`<br>`, `<code>`, `<b>`), since Anki renders HTML;
  - return at most *N* cards in the requested language, with 1–3 short tags.

### 3.2 Persistence

- New aggregate **`FlashcardDeck`** with child **`Flashcard`** records, persisted in SQLite, so a
  (paid) generation is not lost on page reload and cards can be edited before export.
- **The CSV itself is never stored.** Only the structured cards (front/back/tags) are persisted;
  the Anki CSV is built on the fly from the current cards on every export
  (`GET decks/{id}/export`). This keeps a single source of truth — edits to a card are
  automatically reflected in the next export, and no stale file copies pile up in the database.
- Ownership follows the existing pattern: exactly one of `CourseId` / `SemesterId`, copied from
  the source note/document. The deck also stores `SourceType` (`Note` | `Document`), `SourceId`,
  `SourceTitle` (snapshot), and the `Model` used.
- Soft delete for decks (`IsArchived`, `Archive`/`Restore`) like every other aggregate; single
  cards are hard-deleted (they are owned by the deck and have no own lifecycle).
- One migration: `AddFlashcards`.

### 3.3 Anki CSV format

Anki (2.1.54+) understands header lines in imported text files, so the export needs no manual
field mapping in the import dialog:

```
#separator:Semicolon
#html:true
#notetype:Basic
#deck:StudyHub::<Course name>::<Deck title>
#tags column:3
Front;Back;Tags
"What does Dijkstra assume about edge weights?";"All weights are non-negative.<br>A negative edge could lower an already finalized distance.";dijkstra graphs
```

- UTF-8 (no BOM issues: Anki handles both; we write without BOM).
- Every field quoted; `"` escaped as `""`; line breaks converted to `<br>`.
- Tags: space-separated, spaces inside a tag replaced by `_`.
- File name: `<deck-title>.csv` (sanitized).

### API endpoints (`api/flashcards`)

| Method | Route | Purpose |
| --- | --- | --- |
| `POST` | `decks/generate` | Generate + persist a deck from `GenerateFlashcardsRequest` → `FlashcardDeckDto` |
| `GET` | `decks` / `decks/by-course/{id}` / `decks/by-semester/{id}` | List decks (without cards) |
| `GET` | `decks/{id}` | Deck with cards |
| `PUT` | `decks/{deckId}/cards/{cardId}` | Edit a card |
| `DELETE` | `decks/{deckId}/cards/{cardId}` | Remove a card |
| `POST` | `decks/{id}/archive` / `decks/{id}/restore` | Soft delete / restore |
| `GET` | `decks/{id}/export` | Anki CSV (`text/csv`) |

### Dependency notes

- `Logic.Business` already references `Logic.Integration` and uses `IFlashcardGenerator` from
  there — no new project reference needed. `Logic.Integration` keeps referencing only `Shared`
  (plus the new NuGet packages). LAY-7 stays intact:
  Integration still never references Business/Domain.
- The Anthropic SDK and OpenXml packages are only referenced by `Logic.Integration`. The UI also
  references `Logic.Integration` (for accessors) but never registers/uses the AI generator.

## 5. Database Impact

Migration `AddFlashcards`:

- `FlashcardDecks`: `Id` (PK), `Title` (≤200), `SourceType` (string/int), `SourceId` (Guid),
  `SourceTitle` (≤200), `Model` (≤100), `CourseId` (FK, nullable, Restrict),
  `SemesterId` (FK, nullable, Restrict), `IsArchived`, `CreatedAt`, `UpdatedAt`.
  Check constraint: exactly one of `CourseId`/`SemesterId`.
- `Flashcards`: `Id` (PK), `DeckId` (FK, **Cascade** — cards have no life without their deck),
  `Front` (≤1000), `Back` (≤4000), `Tags` (≤500), `Position` (int, keeps generated order).
- `SourceId` is intentionally **not** a FK (it can point to a note or a document); if the source
  is archived later the deck stays valid thanks to `SourceTitle`.

## 7. Validation Plan

- `dotnet build` without new warnings, `dotnet test` green.
- Unit tests (xUnit + Moq), **no real API calls in tests**:
  - `AnkiCsvSerializer`: quoting, `""` escaping, semicolons/newlines in fields, tags with spaces,
    header lines, umlauts (UTF-8).
  - `FlashcardDeckLifecycle`: validation rules, owner invariant, archive/restore.
  - `FlashcardOrchestrator`: note vs. document (PDF/DOCX) source routing, archived/missing source,
    generator failure propagation, owner copied from source, export.
  - `ClaudeFlashcardGenerator`: response → `GeneratedFlashcard` mapping and stop-reason handling,
    tested against a fake/stubbed response (mapping kept in a separately testable method).
- Data tests (`UseInMemoryDatabase`): repository CRUD, cascade of cards.
- Api tests (`WebApplicationFactory`) with a fake `IFlashcardGenerator`: generate, export content
  type, 404/400 problem details, "AI not configured" response.
- Manual: generate a deck from a real note and a real PDF, import the CSV into Anki desktop and
  check fields, HTML rendering, tags, and deck name.

## 8. Risks / Assumptions / Open Questions

- **Cost:** each generation is a paid API call (a 50-page PDF can be ~50–100k input tokens).
  Mitigations: card-count cap, effort `medium`, model configurable; no automatic regeneration.
- **Latency:** generation can take up to a minute or more → long accessor timeout + spinner;
  Blazor Server circuit stays alive meanwhile. Streaming is a later improvement.
- **Quality:** AI cards can be wrong. Cards are always editable before export and the prompt binds
  Claude to the source material. Scanned PDFs without a text layer work (Claude reads the page
  images) but with lower reliability.
- **Privacy:** note/document content is sent to Anthropic. The UI shows a short hint in the
  generate dialog.
- **Very large sources:** if a source exceeds the request limit the user gets a clear validation
  error — content is never silently truncated. Chunking is a later improvement.
- **Documentation inconsistencies found while planning** (to be clarified, not guessed):
  1. `CLAUDE.md` says Integration contains "AI Providers", but its Entity Framework section reserves
     `Infrastructure` for "AI provider adapters". This plan follows the Integration placement
     (also what `docs/agent-context.md` names as the intended home).
  2. `CLAUDE.md` / `docs/agent-context.md` describe `Contracts/` subfolders, entities in
     `Logic.Domain` and repository contracts in `Logic.Domain`; the code actually uses separate
     `*.Contract` projects (`Logic.Domain.Contract`, `Logic.Business.Contract`,
     `Data.Contract`, `Logic.Integration.Contract`), entity records in `Shared`, and `*Lifecycle`
     domain services. This plan follows the **current code**; the docs should be updated
     separately. Exception (per review): the AI integration contract `IFlashcardGenerator` lives
     in `StudyHub.Logic.Integration` itself, not in `Logic.Integration.Contract`.
- **Open questions for review:**
  1. Persist decks/cards (this plan — cards only, never the CSV) or start even smaller with
     "generate → preview → download" and no database? Persisting costs one migration but keeps
     paid results and allows editing.
  2. Default model `claude-opus-5-5` vs. the cheaper `claude-sonnet-5-5`?
  3. Default card language: same as the source, or always German?
