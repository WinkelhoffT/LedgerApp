# Feature Plan: Own Flashcard System (Decks, Spaced Repetition, Anki CSV Import)

Status: Implemented on `feature-IntegrateAnkiApi` (see section 12 for the answers to section 10
and the deviations from this plan).
Classification (per `CLAUDE.md`): **Large**. It adds a new persistent domain with three tables,
a scheduling algorithm, a file import and four new pages.

Replaces the dropped plan `docs/plans/anki-due-cards-plan.md`, which read due counts from an
external Anki sync server. That plan is gone: StudyHub now keeps the cards itself and schedules
them itself. **Anki is only the model.** Nothing runs outside StudyHub: no Anki desktop, no
AnkiConnect, no sync server, no Python.

## 1. Goal

StudyHub gets a small flashcard system of its own, modeled on Anki:

- **Decks** hold Basic cards (front / back / tags).
- Cards are **studied with spaced repetition**: show the front, reveal the back, rate with
  *Again / Hard / Good / Easy*. The rating decides when the card comes back. This is Anki's
  classic SM-2 scheduler with Anki's default deck options.
- Cards get into a deck in three ways:
  1. typed in by hand;
  2. generated by Claude from a Markdown note (the existing generator, now with "Save to deck");
  3. **imported from a CSV/text file in exactly Anki's import format** (section 4). Existing Anki
     decks exported as "Notes in Plain Text" can be imported, and so can StudyHub's own export.
- The Dashboard shows how many cards are **due today** (new / learning / review), like Anki's deck
  list. This was the goal of the dropped plan.

## 2. Scope

In scope:

- Deck management: create, rename, link to a course (optional), set daily limits, archive, restore.
- Card management per deck: list, search, add, edit, delete.
- Study session per deck with Anki's four buttons and the next interval shown on each button
  (`<1m`, `<10m`, `1d`, `4d`, …).
- Anki CSV import (section 4), including the file headers, delimiter detection, quoting, HTML
  handling and duplicate handling.
- Deck export in the same format. The existing `AnkiCsvSerializer` already writes it, so an
  export can be imported again by StudyHub or by Anki.
- Saving AI-generated cards into a deck.
- Dashboard card "Flashcards due today".
- Review log (one row per answer). It is needed for the daily limits, and later analytics can
  build on it.

Out of scope (follow-ups, section 11):

- FSRS (Anki's newer scheduler), interval fuzz, leech detection, suspend / bury, undo.
- Cloze cards, reversed cards, own note types or card templates.
- Media: images, audio and `[sound:…]` references. The CSV has no media files anyway.
- `.apkg` / `.colpkg` import, and importing Anki's scheduling state (the text format carries none).
- Sub-deck hierarchy. Names may contain `::`, but decks stay flat.
- Studying several decks at once ("study all"), custom study, a statistics page.

## 3. Scheduling (Domain rules)

### 3.1 Card states

`New` → `Learning` → `Review` ⇄ `Relearning`. Per card StudyHub stores: `State`, `Step` (index
in the learning or relearning steps), `DueAt` (UTC), `IntervalDays`, `EaseFactor` (in permille as
in Anki, start value 2500 = 250 %), `Reps`, `Lapses` and `LastReviewedAt`.

### 3.2 Algorithm: Anki's SM-2 with Anki's default deck options

The values are fixed constants in the Domain, not settings. They are Anki's defaults:

| Option | Value |
| --- | --- |
| Learning steps | 1 min, 10 min |
| Graduating interval | 1 day |
| Easy interval | 4 days |
| Relearning steps | 10 min |
| Minimum interval after a lapse | 1 day (new interval factor 0 %) |
| Starting ease | 250 % (minimum 130 %) |
| Hard multiplier / Easy bonus | 1.2 / 1.3 |
| Maximum interval | 36,500 days |
| Learn-ahead limit | 20 min |

Rules:

- **New / Learning:**
  - *Again* goes back to step 1.
  - *Hard* on the first step waits the average of steps 1 and 2 (5.5 min); on later steps it
    repeats the current step. With only one step, *Hard* waits 1.5 × that step.
  - *Good* moves to the next step; after the last step the card graduates to `Review` with 1 day.
  - *Easy* graduates at once with 4 days.
- **Review**, with interval `I`, ease `E` and `late` = days overdue:
  - *Again*: lapse. `Lapses + 1`, `E − 200` (minimum 1300), new interval 1 day, then `Relearning`
    (10 min).
  - *Hard*: `max(I + 1, I × 1.2)`, `E − 150`.
  - *Good*: `max(Hard + 1, (I + late / 2) × E)`.
  - *Easy*: `max(Good + 1, (I + late) × E × 1.3)`, `E + 150`.
  - All intervals are capped at 36,500 days.
- **Relearning:** *Again* goes back to the first relearning step, *Hard* waits 15 min (1.5 × the
  only step). *Good* on the last step, or *Easy* on any step, returns the card to `Review` with
  the interval set at the lapse.
- No fuzz: every interval is deterministic, which keeps the tests exact. Fuzz is a follow-up.

### 3.3 Study day and daily limits

- A study day starts at **04:00 Europe/Berlin**, like Anki's "next day starts at 4". The time
  zone and the hour come from `FlashcardStudyOptions` (`Flashcards:TimeZone`,
  `Flashcards:DayStartHour`).
- A `Review` card is due at the start of its due day. "Due today" therefore means
  `DueAt < start of tomorrow`.
- Each deck has its own limits: **new cards per day** (default 20) and **reviews per day**
  (default 200). What has been used today is counted from the review log.
- **Queue order within a deck:**
  1. learning and relearning cards due now or within the learn-ahead limit (20 min);
  2. review cards due today, oldest first, up to the review limit;
  3. new cards in the order they were added, up to the new-card limit.
- **Counts** shown on the deck list, in the study header and on the Dashboard:
  - *new* = `min(new cards in deck, new-card limit − new cards studied today)`
  - *learning* = learning and relearning cards due today
  - *review* = `min(review cards due today, review limit − reviews done today)`
- The study session has no server-side session state. After every answer the server picks the
  next card from the database again (ADR01-001).

## 4. Anki CSV Import

The parser follows Anki's own text importer as of Anki 2.1.55+
(`rslib/src/import_export/text/csv/metadata.rs` and `import.rs` in `ankitects/anki`; checked
against the current source on 2026-10-08).

### 4.1 File

- UTF-8, with or without a BOM. Any other encoding is rejected with a clear message.
- Line endings `\n` or `\r\n`. File extensions `.csv`, `.txt` and `.tsv`.
- Limits: 5 MB per file and 5,000 data rows.

### 4.2 Header lines (only at the start of the file)

| Header | Meaning in StudyHub |
| --- | --- |
| `#separator:` | `Comma`, `Semicolon`, `Tab`, `Space`, `Pipe`, `Colon` (any case) or a single literal character |
| `#html:` | `true` / `false` |
| `#tags:` | tags added to every row (space-separated) |
| `#columns:` | column labels, split by the separator. `Front` and `Back` are matched to the card fields (any case). |
| `#deck:` | target deck name for all rows |
| `#notetype:` | note type for all rows (section 4.5) |
| `#deck column:` / `#notetype column:` / `#tags column:` / `#guid column:` | 1-based column numbers |
| `#if matches:` | `update current` / `keep current` / `keep both` (section 4.6) |

- Keys are matched without regard to case or surrounding spaces. Unknown keys are ignored,
  as in Anki. `#match scope:` is read but ignored, because StudyHub always matches within the
  target deck.
- An old-style first line `tags:foo bar` (without `#`) is supported too.
- `#separator` must come before `#columns`, because the columns are split by it. Anki has the
  same rule.

### 4.3 Data rows

- The delimiter comes from `#separator`. Without a valid one, StudyHub detects it like Anki: in
  the first 8 KiB after the header, the first of **Tab, Pipe, Semicolon, Colon, Comma, Space**
  that occurs anywhere wins. If none occurs, Space is used.
- Quoting as in RFC 4180: fields in `"…"`, an inner quote written as `""`, and quoted fields may
  span several lines.
- A line that **starts with `#`** is a comment, also after the header. Anki configures its CSV
  reader the same way.
- Rows may have different lengths. A missing column counts as empty.
- **HTML:** `#html:true` takes fields unchanged. `#html:false` HTML-escapes each field and turns
  `\n` into `<br>`. Without the header the file counts as HTML if one field in the first 5 rows
  contains an HTML tag. All three rules are Anki's.
- **Field mapping:** if `#columns` names `Front` and `Back`, those columns are used. Otherwise the
  first two columns that are not a deck, note type, tags or GUID column are used. Further columns
  are ignored.
- **Tags** from the tags column are split on whitespace. Tags from `#tags:` are added.
- The **GUID column** is ignored, since StudyHub has no Anki note identity. Duplicates are found by
  the front text instead (section 4.6).

### 4.4 Target deck

- In the import dialog the user picks the target deck: an existing deck, or a new deck named after
  the file.
- Rows with deck information from `#deck:` or the deck column go into the deck of that name. The
  deck is found by name (any case) or created. The file wins over the dialog, as in Anki.

### 4.5 Note types

- Rows whose note type contains `Cloze` are **skipped** and reported ("Cloze notes are not
  supported yet").
- All other note types are imported as Basic, from the first two mapped fields. For "Basic (and
  reversed card)" this means only the forward card is created (follow-up: reverse cards).

### 4.6 Duplicates

- A row is a duplicate if the target deck already has a card with the same front (after trimming).
- The setting comes from `#if matches:`, otherwise from the dialog. The dialog's default is
  **Update current**, Anki's default.
  - *Update current*: back and tags are overwritten, and the learning progress stays.
  - *Keep current*: the row is skipped.
  - *Keep both*: a new card is added.

### 4.7 Result

The import is **all or nothing at file level**: a missing file, a wrong encoding, a file that is
too large, or no usable row at all cancels the whole import. **Single bad rows** are skipped and
listed with their line number. Examples: front or back empty or too long, too many tags, Cloze.
The result shows the counts "added / updated / skipped (duplicate) / failed" and the affected
decks.

## 6. Database Impact

One migration, **`AddFlashcardDecks`**, with three new tables. Existing tables stay as they are.

| Table | Columns | Keys / indexes |
| --- | --- | --- |
| `FlashcardDecks` | `Id`, `Name` (200), `CourseId?`, `NewCardsPerDay`, `ReviewsPerDay`, `IsArchived`, `CreatedAt`, `UpdatedAt` | `Name` unique; FK `CourseId` → `Courses` with `Restrict` |
| `Flashcards` | `Id`, `DeckId`, `Front` (2,000), `Back` (10,000), `Tags` (space-separated, 600), `SourceNoteId?`, `State`, `Step`, `DueAt`, `IntervalDays`, `EaseFactor`, `Reps`, `Lapses`, `LastReviewedAt?`, `CreatedAt`, `UpdatedAt` | FK `DeckId` with `Restrict` (decks are only archived); FK `SourceNoteId` → `Notes` with `Restrict`; index `(DeckId, State, DueAt)` |
| `FlashcardReviews` | `Id`, `FlashcardId`, `ReviewedAt`, `Rating`, `StateBefore`, `IntervalDaysBefore`, `IntervalDaysAfter`, `EaseFactorAfter` | FK `FlashcardId` with `Cascade`; index `(FlashcardId)`, `(ReviewedAt)` |

- **Decks** are soft-deleted (`IsArchived`), like Course and Note. An archived deck shows no due
  cards.
- **Cards** are deleted for real, as in Anki. A deleted card takes its review log rows with it
  (`Cascade`). This differs on purpose from the soft-delete convention: a single card is content,
  not an aggregate that other data hangs on.

## 7. UI

Labels are in English like the rest of the UI. Cards are written in German.

- **`/flashcards`: deck overview** (replaces the generator as the start page). It shows a table
  of decks with course, number of cards, and the counts *new / learning / review* in Anki's
  colors (blue / red / green). Each row has *Study*, *Open* and *Export* actions. At the top are
  the buttons *New deck*, *Import* (dialog: file, target deck, duplicate mode, then the result
  report) and *Generate with AI*. There is also an empty state per mockup.
- **`/flashcards/decks/{id}`: deck detail.** Settings (name, course, both daily limits), card
  table with search (front, back, tags, state, due), add / edit / delete card, export, archive.
- **`/flashcards/study/{deckId}`: study session.**
  - The header shows the deck name and the counts.
  - The front is shown first. *Show answer* (Space) reveals the back below a separator.
  - Four buttons *Again / Hard / Good / Easy* show the next interval; keys `1`–`4` work too.
  - At the end: "Congratulations! You have finished this deck for now."
- **`/flashcards/generate`: the existing generator, moved.**
  - *Export for Anki* is replaced by **Save to deck**: pick an existing deck, or create a new one
    (name prefilled with the note title, course taken from the note). Saved cards keep
    `SourceNoteId`.
  - The link on the Notes page changes to `flashcards/generate?noteId=…`.
- **Dashboard:** the card "Flashcards due today" shows the totals, the 5 decks with the most due
  cards, and a *Study* link per deck. Empty state: "Nothing due today".

## 10. Open Questions, Risks, Assumptions

### Open (please answer before implementation)

1. **Scheduler:** is Anki's classic **SM-2** with Anki's defaults (section 3.2) enough for now? It
   is small, well documented and exact to test. **FSRS**, Anki's current default, schedules more
   accurately, but it needs a model with 19+ parameters and their optimization, so it would make
   this feature much bigger. Recommendation: SM-2 now, FSRS as a follow-up.
2. **Generator export:** may the direct "Export for Anki" button on the generator page go away?
   Its replacement is "Save to deck" plus the deck export. Recommendation: yes, one path instead
   of two.
3. **Branch:** the work happens on `feature-IntegrateAnkiApi`. The name no longer fits, since
   nothing is integrated anymore. Keep it, or switch to a new branch (e.g.
   `feature-FlashcardStudy`)?

### Assumptions

- Single-user operation, as in the whole app so far: no user ID on decks, cards or reviews.
- The study day boundary uses the time zone confirmed earlier (Europe/Berlin) and Anki's 04:00.
- "Same CSV format as Anki" means Anki's text importer (2.1.55+) as described in section 4,
  including the headers. Anki's packages (`.apkg`) are not part of it.

### Risks

- **Imported HTML:** Anki decks can contain any HTML and CSS. StudyHub shows only an allowlist of
  tags without attributes, so styling is lost. Images and audio do not appear, because the CSV
  carries no media.
- **Duplicate check by front:** cards with the same front but different meanings in one deck
  are treated as duplicates. Anki has the same behavior (first field per note type). *Keep both*
  avoids it.
- **Limits:** front 2,000 and back 10,000 characters. Rows above that are reported, not cut off.
- **SM-2 without fuzz:** cards added on the same day stay due on the same days. With many imported
  cards this causes peaks. Fuzz is a small follow-up.
- **UIX-002:** UI strings stay hardcoded like in the rest of the app; there is no localization
  infrastructure yet.

### Documentation inconsistencies found while planning

Reported per `CLAUDE.md`, not resolved by guessing:

1. Like in `flashcards-plan.md`: `docs/agent-context.md` places entities and repository contracts
   in `Logic.Domain`, while the code has entity records in `Shared` and repository contracts in
   `Data.Contract`. This plan follows the code.
2. NAM-005 does not list the suffixes `Lifecycle`, `Serializer`, `Calculator` and `Generator`,
   which the code already uses. New Domain classes use allowed suffixes (`Processor`, `Provider`,
   `Parser`, `Validator`). For deck and card lifecycles this plan keeps the existing `*Lifecycle`
   pattern for consistency.
3. TST-001 asks for FluentAssertions, but the test project does not reference it and uses xUnit's
   `Assert`. The new tests follow the existing project, since adding the package would need
   DEP-001 approval.

## 12. Implementation Notes

### Answers to the open questions (section 10)

1. **Scheduler:** SM-2 with Anki's defaults as recommended; FSRS stays a follow-up.
2. **Generator export:** removed as recommended. The generator saves to a deck, and decks are
   exported from the deck overview and the deck page.
3. **Branch:** the work stayed on `feature-IntegrateAnkiApi`, the branch this task was assigned to.

### Deviations from the plan

- **Four orchestrators instead of three.** Deck CRUD with counts plus card CRUD would have needed
  nine dependencies (COD-006 allows seven), so card listing/adding/editing/deleting and "save to
  deck" live in `DeckCardOrchestrator`; `FlashcardDeckOrchestrator` keeps deck CRUD and counts.
  `FlashcardDeckController` calls both, plus `FlashcardTransferOrchestrator` for import/export.
- **Queue order follows Anki more closely than section 3.3 states:** learning cards that are due
  *now* come first, then reviews, then new cards; a learning card that is only due within the
  20-minute learn-ahead limit is shown early only when nothing else is left. With the order as
  written, a card answered *Again* (due in 1 minute) would come back immediately even when other
  cards are waiting.
- **Answer guard:** answering a card that is not in today's queue (e.g. a review due next week, or a
  repeated submit after a new card already graduated) returns `409` with
  `flashcard_not_due` (`FlashcardNotDueException`, not in the plan's exception list). Learning
  cards within the learn-ahead limit stay answerable, so a slow answer is never rejected because
  another card became due meanwhile.
- **Clock:** `StudyDayProvider` reads `TimeProvider` and returns a `StudyDay` (now, date, start,
  next start); the review processor and queue provider take that value instead of reading the
  clock, so one request uses one instant. Lifecycles read `TimeProvider` for timestamps.
- **New-card order:** a new card's `DueAt` is its queue position (creation time plus one tick per
  card of a batch), so cards keep the order they were added in without an extra column.
- **Intervals** are rounded half away from zero to whole days, as in Anki's current scheduler.
- **Import details:** `#columns` is split after the delimiter is known (so `#columns` before
  `#separator` also works); a column labelled `Tags` is used as the tags column when no
  `#tags column` is set; a file without data rows, or whose rows all fail, is rejected with the
  first failure's line and reason; rows naming an archived deck fail; the dialog's "new deck named
  after the file" reuses an existing deck of that name.
- **Startup validation:** `Flashcards:TimeZone` and `Flashcards:DayStartHour` are validated with
  `ValidateOnStart` in StudyHub.Api; the Domain receives the plain `FlashcardStudyOptions` object,
  so it needs no Options package.
- **`FlashcardHtmlFormatter`** renders the allowed tags with their attributes dropped (an imported
  `<span style="…">` becomes `<span>`); other tags stay visible as text, as before.
- **Study page:** `Enter` also reveals the answer; a small script keeps `Space` from scrolling the
  page while the study area has focus.

### Decks for a semester (added after review)

A deck can also belong to a **semester** instead of a course, e.g. for a workshop that is set up as
a semester. `FlashcardDeck` got a nullable `SemesterId`; a deck belongs to at most one of a course
or a semester, or to neither (enforced in `FlashcardDeckLifecycle` and by the check constraint
`CK_FlashcardDecks_AtMostOneParent`). As with courses, an archived semester cannot be newly linked,
but a deck that is already linked keeps it. Separate migration `AddFlashcardDeckSemester` (FK to
`Semesters` with `Restrict`, index on `SemesterId`), since `AddFlashcardDecks` may already be
applied (DAT-006). In the UI the deck dialog offers courses and semesters in one "Belongs to"
dropdown, and "Save to deck" in the generator gives a new deck the note's course or semester.

### Target deck chosen before generating (added after review)

The generator's options include the **deck** the cards go to (an existing deck or "New deck…" with
a name that follows the selected note's title until the user types one). After reviewing the cards,
"Save to <deck>" stores them there; nothing is saved without that click. `/flashcards/generate?deckId=…`
preselects the deck, and the deck page links to it with "Generate with AI". This is UI only: the
generation request is unchanged, and saving still uses `AddFlashcardsRequest`.
